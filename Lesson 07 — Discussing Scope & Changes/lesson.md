# LESSON 07 — Discussing Scope & Changes

## 1. Overview

**Target Level:** Level 2  
**Target WPM:** 130–145  
**Target Turn Length:** 12–20 words  
**Target Turns:** 16–22  
**Characters:** 2–3  
**IT Context:** Scope / change requests / sprint planning  
**Meeting Type:** Requirement and scope discussion  
**Listening Objective:** Understand when a client or PM changes scope, adds requirements, or discusses impact and trade-offs.  
**Speaking Objective:** Discuss the impact of changes, clarify whether they are in scope, and communicate trade-offs.  
**Grammar Focus:** Present perfect, modal verbs, basic conditionals  
**Reduced Speech:** Moderate  
**Context Noise:** Low

---

# 2. Situation

The team has already agreed on the basic checkout scope for the sprint.

During a follow-up meeting, Sarah tells David that the client has requested an additional change.

The new request sounds small, but it may affect:

- frontend work
- backend logic
- testing
- the current sprint
- the delivery timeline

David needs to understand the change and determine whether it is still within the agreed scope.

The key skill is not simply saying:

> “Okay, we can do it.”

A developer needs to understand:

> **What changed → What is affected → Is it in scope → What is the impact → What are the options?**

---

# 3. IT Context

The team is developing a new **checkout flow**.

The original scope includes:

- customer address
- payment method
- order confirmation

The client now wants customers to be able to **edit their shipping address after selecting a payment method**.

This may require changes to:

- checkout UI
- backend validation
- order data
- QA test cases

David needs to discuss whether the change can fit into the current sprint.

---

# 4. Learning Objectives

By the end of this lesson, you should be able to:

1. Understand when someone introduces a scope change.
2. Recognize phrases such as:
   - “The client has asked for...”
   - “They also want...”
   - “Can we include this...?”
   - “Is that still in scope?”
3. Ask what parts of the system are affected.
4. Explain whether a change is small or likely to require additional work.
5. Discuss trade-offs between scope and timeline.
6. Suggest options instead of simply accepting or rejecting a request.
7. Confirm the final decision.

# 6. Business Meeting Patterns

## 6.1 Introducing a Change

### “The client has asked for...”

Useful when reporting a new client request.

Examples:

> The client has asked for one more change.

> The client has asked for an additional validation step.

> They've also asked for a new option on the checkout page.

Notice the **present perfect**:

> has asked

This connects a past request to the current situation.

---

## 6.2 Checking Scope

### “Is that still in scope?”

Very common in project discussions.

Other useful forms:

> Is this still in scope?

> Is that part of the current scope?

> Was this included in the original requirement?

> Are we still planning to include this?

The important concept:

```text
Original scope
      ↓
New request
      ↓
Still in scope?
      ↓
Impact / decision
```

---

## 6.3 Asking About Impact

Useful patterns:

> How much work would that involve?

> Would that affect the backend?

> Would this require changes to the frontend?

> Does that impact the current timeline?

> Would we need additional QA?

These questions help you understand the cost of a change.

---

# 7. Discussing Trade-offs

A realistic developer does not always answer:

> “Yes, we can do it.”

Instead, you may need to explain the trade-off.

### Pattern 1

> We can do that, but it might push the testing back.

### Pattern 2

> We could include it, but we'd need more time.

### Pattern 3

> If we add this now, we may need to move another task to the next sprint.

### Pattern 4

> We can keep the deadline, but we'd need to reduce the scope somewhere else.

These are important Business English patterns because they let you **negotiate professionally**.

---

# 8. Natural Meeting English

## Textbook

> This requirement will have an impact on the current implementation and timeline.

## Natural

> That could affect the current timeline.

---

## Textbook

> Is it possible to include this requirement within the current sprint?

## Natural

> Can we fit this into the current sprint?

---

## Textbook

> We would need additional development and testing time.

## Natural

> We'd need some extra development and QA time.

---

## Textbook

> If we implement this change, another task may have to be postponed.

## Natural

> If we add this now, we might have to push another task back.

---

# 9. Natural / Reduced Speech

At Level 2, listen for contractions and connected phrases.

## “They've also asked for...”

> They've also asked for...

The words **they have** may be reduced into:

> They've

Recognize the chunk:

> **They've also asked for...**

---

## “Would that affect...?”

The beginning may be less stressed.

Focus on:

> **affect the backend**

---

## “We'd need...”

> We would need → We'd need

Example:

> We'd need some extra QA time.

---

## “We could...”

This often introduces an option or compromise.

Example:

> We could move that to the next sprint.

---

## “If we add this now...”

Don't translate word by word.

Recognize the structure:

> **If + change → possible consequence**

# 10. Realistic Conversation

## Scenario

Sarah tells David that the client has requested a change to the checkout flow.

David needs to determine the impact and whether the change can fit into the current sprint.

### Conversation

Sarah: Hey David, the client has asked for one more change to the checkout flow.

David: Okay. What's the change?

Sarah: They want customers to edit their shipping address after selecting a payment method.

David: Got it. Was that included in the original requirement?

Sarah: No, that wasn't part of the original scope.

David: Okay. How much work would that involve?

Sarah: We'd probably need some frontend changes and additional backend validation.

David: Right. Would QA need to update the test cases too?

Sarah: Yeah, I think so. We'd need to cover the new flow.

David: Does that affect the current sprint timeline?

Sarah: It could. We already have a pretty full sprint.

David: Okay. Can we fit this in if we move another task out?

Sarah: Possibly. Which task would you suggest moving?

David: We could move the address history task to the next sprint.

Sarah: That might work. Is the client okay with that?

David: I'm not sure. Should we confirm the priority with them first?

Sarah: Yeah, let's do that before we change the sprint scope.

David: Sounds good. If they want this now, we can explain the trade-off.

Sarah: Exactly. I'll check with the client and update the ticket.

David: Alright. Let me know what they decide.

# 12. Listening Tasks

## Task 1 — Identify the Scope Change

Listen and answer:

1. What is the new client request?
2. Was it part of the original scope?
3. Which technical areas may be affected?

Do not focus on every word.

First identify:

> **request → impact**

---

## Task 2 — Identify Impact

Listen for statements about:

- frontend
- backend
- QA
- sprint
- timeline

Write down which areas are affected.

---

## Task 3 — Identify the Trade-off

What solution does David suggest?

What task might be moved to the next sprint?

Why does Sarah want to confirm with the client first?

---

## Task 4 — Listen for Conditional Language

Identify the conditional statements.

Examples:

> If we move another task out...

> If they want this now...

Ask yourself:

> What is the condition?

> What is the possible consequence?

---

# 13. Speaking Patterns

## Asking Whether Something Is in Scope

> Is this still in scope?

> Was this included in the original requirement?

> Is this part of the current sprint?

---

## Asking About Impact

> How much work would that involve?

> Would that affect the backend?

> Would QA need to update the test cases?

> Does that affect the timeline?

---

## Offering Options

> We could move that to the next sprint.

> We could keep the current scope and do this later.

> We could reduce another part of the scope.

---

## Explaining Trade-offs

> We can do that, but we'd need more time.

> We can keep the deadline, but we'd need to reduce the scope.

> If we add this now, we might have to push another task back.

---

# 14. Speaking Task

Imagine the client asks:

> “Can you also add a wishlist button to the product page in this sprint?”

You are the developer.

Do not answer immediately with:

> “Yes.”

Ask questions and discuss:

1. Was the wishlist feature part of the original scope?
2. How much work would it involve?
3. Would backend changes be required?
4. Would QA need additional time?
5. Can it fit into the current sprint?
6. If not, what could be moved to the next sprint?

Try to reach a professional decision.

# 15. AI Role-play Scenario

## Role

**You:** Developer  
**AI:** Project Manager / Client

## Situation

The client introduces a new requirement during an active sprint.

The AI should explain the request naturally but should not immediately tell you whether it is in scope.

Your job is to:

- clarify the change
- ask whether it was part of the original scope
- ask about technical impact
- discuss the timeline
- suggest alternatives
- explain trade-offs
- confirm the final decision

Useful expressions:

> Is that still in scope?

> How much work would that involve?

> Would that affect the timeline?

> We could move this to the next sprint.

> If we add this now, we might have to push something else back.

## Success Condition

You should be able to discuss a change without automatically accepting or rejecting it.

Your goal is:

> **Change → Impact → Options → Trade-off → Decision**
