# LESSON 08 — Confirming Understanding

## 1. Overview

**Target Level:** Level 2  
**Target WPM:** 135–150  
**Target Turn Length:** 12–20 words  
**Target Turns:** 16–22  
**Characters:** 3  
**IT Context:** Client requirement / user flow / business rule  
**Meeting Type:** Requirement confirmation  
**Listening Objective:** Understand when speakers summarize, correct, confirm, or refine a requirement.  
**Speaking Objective:** Summarize requirements clearly and confirm that both sides have the same understanding.  
**Grammar Focus:** Present perfect, modal verbs, basic conditionals  
**Reduced Speech:** Moderate  
**Context Noise:** Low

---

# 2. Situation

Sarah is discussing a new checkout requirement with David and Emily.

The requirement has several parts:

- Customers can save a shipping address.
- The address should be available for future orders.
- Customers can have multiple addresses.
- The default address should be used during checkout.
- Guest users cannot save addresses.

David understands most of the requirement, but before development starts, he needs to summarize it and make sure everyone agrees.

This is an important meeting skill.

Understanding something in your head is not enough.

You need to be able to say:

> **“So, if I understand correctly...”**

and explain the requirement in your own words.

---

# 3. IT Context

The team is working on an **address management feature** for an e-commerce website.

The client wants customers to save shipping addresses and select them during checkout.

However, there are several business rules:

- Only logged-in customers can save addresses.
- Customers can save multiple addresses.
- One address can be marked as default.
- The default address should be selected automatically during checkout.
- Customers can change the selected address before placing the order.
- Guest users must enter an address manually.

The developer needs to confirm all of these rules before implementation.

---

# 4. Learning Objectives

By the end of this lesson, you should be able to:

1. Recognize when someone is summarizing a requirement.
2. Understand confirmation phrases such as:
   - “So, if I understand correctly...”
   - “Just to confirm...”
   - “So you're saying...?”
   - “Does that mean...?”
3. Summarize a technical requirement in your own words.
4. Confirm specific business rules.
5. Correct your understanding when the client says something different.
6. Distinguish between:
   - what the system does
   - what the user can do
   - what the user cannot do
7. End a requirement discussion with a clear shared understanding.

# 6. Business Meeting Patterns

## 6.1 “So, if I understand correctly...”

This is one of the most important patterns in requirement meetings.

Example:

> So, if I understand correctly, logged-in customers can save multiple addresses.

You are not simply asking a question.

You are:

```text
Listen
   ↓
Process
   ↓
Summarize
   ↓
Confirm
```

This shows the client that you are actively following the discussion.

---

## 6.2 “Just to confirm...”

Use this when you want to verify one specific detail.

Examples:

> Just to confirm, guest users can't save addresses, right?

> Just to confirm, the default address is selected automatically?

> Just to confirm, users can change the address before checkout?

This is very common in real meetings.

---

## 6.3 “So you're saying...?”

This is useful when you want to restate what someone said.

Examples:

> So you're saying the default address will be selected automatically?

> So you're saying customers can save multiple addresses?

Be careful with tone.

In a meeting, this should sound like **confirmation**, not confrontation.

---

## 6.4 “Does that mean...?”

Use this when one requirement leads to another possible behavior.

Examples:

> Does that mean guest users have to enter the address manually?

> Does that mean we need to store multiple addresses?

> Does that mean the default address is used automatically?

---

# 7. Confirming Different Types of Information

When confirming a requirement, separate the information into categories.

## User

> Who can use the feature?

## Action

> What can the user do?

## Restriction

> What can't the user do?

## System Behavior

> What does the system do automatically?

## Condition

> What happens if something changes?

For example:

```text
User:
Logged-in customer

Action:
Can save multiple addresses

Restriction:
Guest user cannot save addresses

System behavior:
Default address is selected automatically

Condition:
Customer can change the address before checkout
```

This structure is extremely useful for developers.

# 8. Natural Meeting English

## Textbook

> I would like to confirm whether my understanding of the requirement is correct.

## Natural

> Just to confirm, is this how it should work?

---

## Textbook

> Please confirm that guest users are unable to save shipping addresses.

## Natural

> Just to confirm, guests can't save addresses, right?

---

## Textbook

> If I understand the requirement correctly, the default address will automatically be selected.

## Natural

> So, the default address is selected automatically, right?

---

## Textbook

> Could you please clarify whether customers can change the address before placing the order?

## Natural

> Can customers change the address before they place the order?

# 9. Natural / Reduced Speech

At this level, some phrases may become difficult because several words connect together.

## “Just to confirm...”

In natural speech, this may sound like one chunk:

> “Justta confirm...”

Don't try to separate:

> just → to → confirm

Recognize:

> **Just to confirm...**

---

## “So, if I understand correctly...”

This is a long chunk.

You may hear:

> “So, if I understand correctly...”

with weak pronunciation on some small words.

Focus on:

> **understand correctly**

---

## “You can't...”

> You cannot → You can't

Example:

> You can't save an address as a guest.

---

## “We need to...”

Natural speech may reduce:

> “We need to...”

The important information is usually the verb after it.

Example:

> We need to store multiple addresses.

Focus on:

> **store multiple addresses**

---

## “Right?”

This short word is extremely common at the end of confirmation questions.

Example:

> The default address is selected automatically, right?

Here **right?** means:

> “Đúng không?”

It is not asking for a completely new piece of information.

It is asking for confirmation.

# 10. Realistic Conversation

## Scenario

Sarah explains an address-management requirement.

David summarizes the requirement.

Emily joins the discussion to clarify one business rule related to guest users.

### Conversation

Sarah: Okay, so the client wants customers to save shipping addresses for future orders.

David: Got it. Just to confirm, only logged-in customers can save an address, right?

Sarah: That's right. Guest users can't save addresses.

David: Okay. Can customers save more than one address?

Sarah: Yes, they can save multiple addresses.

David: And can they choose one as their default address?

Sarah: Exactly. The default address should be selected automatically during checkout.

David: So, if I understand correctly, the customer doesn't have to select an address every time.

Sarah: Right. The default one will be selected for them.

David: Okay. Can they change the selected address before placing the order?

Sarah: Yes, they can choose another saved address.

Emily: And what happens if they don't have any saved addresses?

Sarah: They'll need to enter a new shipping address manually.

David: Got it. Does that also apply to guest users?

Sarah: Yes. Guests have to enter their address manually.

David: Okay, so logged-in customers can save multiple addresses, while guests can only enter an address during checkout.

Sarah: Exactly.

David: And the default saved address is selected automatically, but customers can change it before placing the order.

Sarah: That's correct.

Emily: Great. That sounds clear from the QA side.

David: Alright. I think we're on the same page now.

Sarah: Perfect. I'll update the ticket with these rules.

# 12. Listening Tasks

## Task 1 — Identify Confirmation Phrases

Listen for these phrases:

- “Just to confirm...”
- “And can they...?”
- “So, if I understand correctly...”
- “Does that also apply to...?”
- “So...”
- “That's correct.”
- “Exactly.”
- “That's right.”

The goal is to recognize the **function** of the sentence.

Ask yourself:

> Is the speaker asking for new information?

or:

> Is the speaker checking their understanding?

---

# 13. Listening Task 2 — Build the Requirement

Listen and complete:

### Who?

__________ customers can save addresses.

### What?

They can save __________ addresses.

### Default behavior

The __________ address is selected automatically.

### Change

Customers can __________ the selected address before checkout.

### Guest users

Guests have to enter their address __________.

---

# 14. Listening Task 3 — Catch Corrections

Listen carefully to the conversation.

David initially asks:

> “Only logged-in customers can save an address, right?”

Sarah confirms it.

Later David summarizes:

> “Logged-in customers can save multiple addresses, while guests can only enter an address during checkout.”

Notice how David combines several pieces of information into one summary.

This is an important real-world listening skill:

> **Don't just remember individual answers. Build the complete requirement.**

---

# 15. Listening Task 4 — Listen Without the Transcript

First listen without reading.

Try to reconstruct this structure:

```text
Who can use it?
        ↓
What can they do?
        ↓
What can't they do?
        ↓
What happens automatically?
        ↓
What happens in special cases?
```

Only check the transcript after attempting your own summary.

# 16. Speaking Patterns

## Confirm One Detail

> Just to confirm, guests can't save addresses, right?

> Just to confirm, the default address is selected automatically?

---

## Summarize Several Details

> So, if I understand correctly, logged-in customers can save multiple addresses.

> So, the default address is selected automatically, but users can change it before checkout.

---

## Check a Consequence

> Does that mean guests have to enter the address manually?

> Does that mean we need to support multiple saved addresses?

---

## Confirm the Final Understanding

> Okay, I think we're on the same page.

> Alright, that makes sense now.

> Got it. I'll update the ticket with these rules.

---

# 17. Speaking Task

Imagine the client gives you this requirement:

> “Customers can save multiple payment methods. The default payment method should be used automatically during checkout.”

Before implementing it, confirm the details.

Ask about:

1. Logged-in vs guest users
2. Number of payment methods
3. Default payment method
4. Changing the payment method
5. Removing a saved payment method
6. What happens when the default payment method expires

Try to summarize the complete requirement at the end.

Example:

> So, if I understand correctly, logged-in customers can save multiple payment methods, and the default one is selected automatically. Right?

Then continue asking questions.

# 18. AI Role-play Scenario

## Role

**You:** Developer  
**AI:** Client / Project Manager  
**Optional third role:** QA

## Situation

The client explains a new feature with several business rules.

The AI should provide the information gradually rather than explaining everything at once.

Your job is to:

1. Listen.
2. Ask clarification questions.
3. Summarize what you understand.
4. Ask for confirmation.
5. Correct your understanding if necessary.
6. Finish with a clear summary.

Useful expressions:

> Just to confirm...

> So, if I understand correctly...

> Does that mean...?

> So you're saying...?

> And that applies to guest users too, right?

> Okay, I think we're on the same page.

## Success Condition

You should be able to finish the discussion with a summary that contains:

- users
- actions
- restrictions
- system behavior
- conditions

The goal is:

> **Listen → Understand → Summarize → Confirm**
