# LESSON 16 — Project Status

## 1. Overview

- **Target Level:** Level 3
- **Target WPM:** 155–170
- **Turn length:** 18–30 words
- **Turns:** 22–28
- **Characters:** 3
- **IT Context:** Weekly project status / delivery / risk / dependencies
- **Meeting type:** Weekly project status meeting

### Main Goal

Practice following a realistic weekly project status meeting where several topics are discussed quickly: completed work, current work, blockers, QA, deployment, timeline, risks, and next steps.

The key challenge is **topic tracking**. The speaker may move from one subject to another without formally announcing every transition.

Core flow:

> **Overall Status → Completed → In Progress → Risks → Dependencies → Timeline → Next Steps**

---

## 2. Situation

The team is holding its weekly project status meeting for an e-commerce project.

The project includes:

- checkout improvements
- payment integration
- product-page changes
- QA
- production deployment

The PM needs a concise status update for the client.

The team is generally on track, but there are several risks:

- payment API edge cases
- QA capacity
- a pending client decision
- limited timeline buffer

The meeting is no longer a simple stand-up. The speakers need to connect technical details to project-level impact.

---

## 3. IT Context

A typical project-status discussion may cover:

```text
What was completed?
        ↓
What is in progress?
        ↓
What is blocked?
        ↓
What is at risk?
        ↓
What depends on someone else?
        ↓
Are we still on track?
        ↓
What happens next?
```

Useful project-status categories:

- **Green:** on track
- **Yellow:** some risk / needs attention
- **Red:** serious issue / likely delay

In real meetings, people may not explicitly say “yellow status.” Instead, they may say:

> “We're still on track, but there's not much buffer.”

That sentence communicates risk without saying the project is already delayed.

---

## 4. Learning Objectives

### Listening

You should be able to:

- follow a multi-topic project status discussion
- identify completed, ongoing, and blocked work
- distinguish project status from individual task status
- recognize risk and impact statements
- track topic transitions
- understand dependencies
- follow timeline discussion
- identify action items at the end of the meeting

### Speaking

You should be able to:

- give a concise project-level update
- summarize multiple workstreams
- explain project risks
- connect technical issues to delivery impact
- communicate dependencies
- discuss whether the project is on track
- summarize next steps

## 6. Business Meeting Patterns

### Giving a status summary

> **Overall, we're still on track.**

> **Most of the development work is complete.**

> **We're making good progress on the backend side.**

> **There are a couple of things we need to keep an eye on.**

### Talking about risk

> **The main risk at the moment is...**

> **That could have an impact on the timeline.**

> **We're okay for now, but there's not much buffer.**

> **It's not blocking us yet, but it could become an issue.**

### Talking about dependencies

> **We're waiting on the client to confirm...**

> **That depends on QA's availability.**

> **We're still waiting for the API team.**

### Moving between topics

> **Moving on to...**

> **On the frontend side...**

> **As for the deployment...**

> **One other thing...**

> **Before we wrap up...**

### Closing the status meeting

> **So, to summarize...**

> **The main action items are...**

> **I'll follow up on that.**

> **Let's keep that as a watch item for now.**

## 7. Project Status vs Task Status

A task-level update:

> “I finished the backend validation.”

A project-level update:

> “The checkout backend is complete, and we're now moving into QA.”

Project status focuses on **impact and overall progress**, not every implementation detail.

A useful project-status answer often looks like:

> **Status → Progress → Risk → Impact → Next Step**

Example:

> “We're still on track. Backend is complete and frontend is almost done. The main risk is the payment API, which could push QA back if we find more edge cases.”

---

## 8. Risk vs Blocker

### Blocker

Something that currently prevents progress.

> **We're blocked because we don't have the API credentials.**

### Risk

Something that may cause a problem.

> **The API edge cases are a risk because they could push QA back.**

Important:

> **A risk is not necessarily a problem yet.**

This distinction is very common in project meetings.

## 9. Natural Meeting English

| Formal / textbook | Natural meeting English |
|---|---|
| Please provide the overall project status. | Overall, how are we looking? |
| What is the current status? | Where are we at? |
| What problems should we monitor? | Anything we need to keep an eye on? |
| There is a possible schedule impact. | That could push the timeline back. |
| We are currently waiting for the client. | We're still waiting on the client. |
| This issue does not currently block development. | It's not blocking us yet. |
| Let us discuss another topic. | Moving on to... |
| Please summarize the next actions. | What are the action items? |
| We will discuss this later. | Let's follow up on that. |

## 10. Natural / Reduced Speech

### 1. Where are we at?

This is a very common spoken way to ask:

> “Tình hình hiện tại thế nào?”

It does not mean asking for a physical location.

### 2. We're still waiting on the client.

**waiting on** is common in business speech.

Meaning:

> đang chờ phía client xử lý / phản hồi.

### 3. Anything we need to keep an eye on?

This can sound like one long chunk.

Focus on:

> **keep an eye on**

### 4. It's not blocking us yet.

**It's** and **not** can be compressed in natural speech.

The important meaning is:

> currently not a blocker, but that could change.

### 5. How are we looking?

This is an indirect way of asking about overall status.

### 6. Let's follow up on that.

A common meeting phrase meaning:

> tiếp tục xử lý / theo dõi vấn đề đó sau meeting.

## 11. Realistic Conversation

### Characters

- **Sarah** — Project Manager
- **David** — Developer
- **James** — Tech Lead

### Conversation

**Sarah:** Alright, let's go through the project status. Overall, how are we looking for this week?

**David:** We're still on track. The checkout backend is complete, and I've finished most of the payment integration.

**Sarah:** Okay. What's left on the payment side?

**David:** There are a few API edge cases I still need to handle. The main flow is working, but I want to cover the failed-payment responses before we call it done.

**James:** Are those blocking anything right now?

**David:** No, not yet. I can continue with the implementation, but they could affect the timeline if the provider has more response variations.

**Sarah:** Got it. So that's a risk rather than a blocker.

**David:** Exactly.

**Sarah:** How about the frontend?

**David:** The checkout UI is almost finished. There are a couple of validation messages left, and then it should be ready for QA.

**James:** Have you already pushed the latest changes to staging?

**David:** Yeah, most of them are on staging. I'm planning to push the remaining changes this afternoon.

**Sarah:** Okay. Moving on to QA, do we still have capacity to start testing tomorrow?

**James:** We should, but QA is also covering the product-page changes this week.

**Sarah:** Could that affect the checkout testing?

**James:** It might. We have enough capacity for the main flow, but regression testing could take longer than expected.

**David:** If QA needs more time, I can prioritize the payment scenarios first.

**Sarah:** That sounds reasonable. What about the client-side dependency?

**David:** We're still waiting on the client to confirm one payment error message.

**Sarah:** Is that blocking the release?

**David:** No. We can use the current message for now, but we'd need to update it if the client wants different wording.

**James:** And that change should be small.

**Sarah:** Okay. As for deployment, are we still targeting Friday?

**David:** Yes, assuming the API testing doesn't uncover anything major.

**James:** I'd say Friday is still realistic, but there's not much buffer if QA slips.

**Sarah:** Understood. What are the main risks we should mention in the client update?

**James:** I'd mention the payment API edge cases and QA capacity.

**David:** I agree. Neither is blocking us right now, but both could affect the timeline.

**Sarah:** Anything else we need to keep an eye on?

**David:** The client confirmation. If they change the payment message late, we'll need to update the frontend and retest it.

**Sarah:** Okay. Let's keep that as a watch item for now.

**James:** Sounds good.

**Sarah:** So, to summarize: backend is complete, frontend is almost done, and we're targeting QA tomorrow and deployment Friday.

**David:** Right.

**Sarah:** The main risks are payment API edge cases, QA capacity, and the pending client confirmation.

**James:** Yep.

**Sarah:** David, you'll finish the remaining payment cases and update staging. James, you'll confirm QA capacity. I'll follow up with the client on the payment message.

**David:** Sounds good.

**James:** Works for me.

**Sarah:** Great. Let's use Friday as the target and flag anything that could put that date at risk.

1. overall status
2. backend
3. frontend

5. payment API
6. client dependency
7. deployment

> “Wait, is that actually blocking us?”
